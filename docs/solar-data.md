# Локальные данные Solar

`src/domain/solar-trip.ts` описывает агрегат Trip: участники, дни и остановки,
расходы с долями в целых тетри, журнал Settlement и неизменяемые снимки курсов.
У всех сущностей есть ID; ссылки проверяются до принятия изменений и при чтении.
Порядок массивов дней, остановок и долей сохраняется. Участника с любой финансовой
историей, включая отменённые переводы, удалить нельзя.

`solar-actions.ts` выполняет атомарные переходы. `trip-finance.ts` преобразует
постоянную целочисленную модель во входной формат проверенных алгоритмов B1–B4.
Расходы сохраняют ссылку на свой снимок курса; новый текущий курс добавляет новый
снимок. Общий селектор считает суммы, остаток бюджета, балансы и рекомендации
для обоих экранов. Доменные типы не импортируют демонстрационные данные.

`SolarRepository` — заменяемый интерфейс load/save. Текущая реализация использует
только AsyncStorage `travel-app/solar/v1`, с `schemaVersion: 1`. Старый AppStore
и `travel-app/state/v1` не меняются и не объединяются с Solar. Неподдерживаемая
версия блокирует загрузку: будущая миграция должна быть явной и проверяемой.
Миграция прежних данных этим этапом не требуется.

`solar-storage.ts` управляет loading/ready/error, подписками и одним писателем.
Демо создаётся только после успешного чтения отсутствующего ключа (`null`) и
сохраняется до ready. Повреждённые или недоступные данные не сбрасываются.
При чтении существующей записи автоматической записи нет. Все новые состояния
валидируются и замораживаются перед публикацией; ранние действия отклоняются.

Быстрые изменения могут объединяться в один снимок; записи строго последовательны.
При ошибке записи последние изменения остаются в памяти, новые действия блокируются.
Кнопка повтора сохраняет именно этот снимок, без повторного чтения старых данных.
Повтор чтения допускается только после ошибки чтения. Автоматического сброса нет.

`SolarTripProvider` расположен в layout Solar. `useSolarTrip` подписывает оба экрана
на активную поездку через useSyncExternalStore. Повторное открытие экрана не
инициализирует демо. После перезапуска читается последний успешно сохранённый
снимок, включая requestId, статусы и отмены платежей, маршрут и участников.
Ошибки хранилища показываются существующим StorageBoundary.

## Проверка

Без установки новых зависимостей:

```sh
npm run test:finance
npm run test:storage
npm run test:solar
./node_modules/.bin/tsc --noEmit
```

Тесты Solar используют внедряемый адаптер памяти, включая ошибки, задержки,
повторное создание хранилища и обработчики экранов. Они не заменяют проверку
браузера или устройства. Реальные пользовательские данные тесты не читают.

## Ограничения этапа

- AsyncStorage сохраняется асинхронно: принудительное завершение процесса до
  окончания записи может потерять ещё не сохранённые изменения. После ошибки
  записи следует повторить сохранение до закрытия приложения.
- Один координатор работает в одном JS-процессе. Согласование нескольких вкладок,
  устройств и серверная синхронизация не реализованы.
- Интерфейс создания и переключения нескольких поездок не добавлен; действия
  модели это поддерживают. Поездка в Грузию, её цены и курс остаются демонстрационными.
- Добавление места пока сохраняет существующую заготовку «Новое место».
  Карты, реальные приглашения, API, SQLite и экспорт/ремонт повреждённых данных
  остаются отдельными задачами.
